# 有界批量工具与单计划授权

本批将模型明确选择的 1～2 份计划交给真实业务服务逐项执行、保存、读取；也支持一次读取 1～3 条当前专业记录。每个子操作独立计入原有 15 事件预算，模型响应仍限五轮。批量控制流程不是额外的模型自主决策。最终Windows754通过/25跳过、Linux763通过/16跳过，均6子测试通过；128相关、schema修复62相关、60前端及构建通过。首次Windows753通过/1失败、Linux762通过/1失败均保留；最终全量另存。两平台测试时间有重叠，不比较平台性能。评分75保持，详[证据索引](AGENT_BATCHES_EVIDENCE.json)和[复评](RESCORE_20261106_BATCHES.md)。

## 已实现的边界

- `calculation_prepare` 只接受本轮冻结的计划键，预检全部选择、权限、来源版本和预算后才开始；每次写入前再次核验。未选计划不自动执行，部分失败保留已写记录，不重复不确定写入。
- `professional_read_many` 预检全部记录归属；计划任务只能读取本任务新建记录。复用写操作时仍重新读取当前状态。
- `execution_authorized: false` 明确暂缓一份计划，工具选项排除它，后端拒绝单项或批量执行，完成提醒不催促执行它。字段为严格布尔值，模型不能在调用参数中改变它。
- 为兼容原有请求，省略上述字段表示随本次请求授权执行。**仅在自然语言中写“稍后确认”不构成可靠的权限约束。**界面已说明这一点，暂缓状态独立显示；后续须继续改善结构化授权的操作体验。
- 模型仍需逐份提交数值事实或限制，最终来源重读保持不变。时间线明确标记“模型选择”和“批量子操作”；结果有效、任务全部完成及工程认证仍分开。

## 独立答案与实际推理

所有新题在真实推理前冻结输入、答案与 SHA256；原失败和修改后的回归分目录保存。实际调用本地 Qwen3-4B 与 Qwen3-8B 的固定公开权重，无训练、无脚本模型答案、无替换计算器。

授权阶段新题包括：采购总额 233.80 USD（分行四舍五入、整数采购量向上取整）；七年声明边界碳排 452.9 kgCO₂e；混合单位墙体 R=2.17 m²·K/W；双失效限制；未知导热系数与完整采购并列；首份计划暂缓而第二份授权。公式与更详细字段见公开用例文件。工具精简后另冻新题：R=.13+.04+.14/.7+.135/(.04×1.25)=3.07，采购31.25×1.04×8.4+ceil(7×1.1)×2.6625=294.30 USD，以及两记录失效延续。它们是合成输入，不是实楼、市场报价、认证因子或专家签署结论。

初始源码 `fc9f23f` 的两模型旧题均 4/4 形成所需核验产物；新题原始检查为 3/6、4/6。新题中碳清单面积 927.2 与测试项目 721 不一致，是夹具错误；应用正确拒绝，后继失效题没有可读记录。修正面积后的题归为已知回归，不能冒充新盲测。4B 还在收到待交付提醒后尝试执行文字中暂缓的计划，说明原先的语义约束不够。该尝试因面积冲突而失败，不能把面积拒绝当成授权防护。

正式结果卡与模型解释分别评估：初始 4B 曾把工期记录失效归因于资源未调平，且对采购失效说明是否完成出现矛盾措辞；正式限制正确不等于这些解释正确。原始文字均留存。

授权约束源码 `6315c6c` 下，4B/8B 各10道已知回归和4道新题均形成所需正式产物，实际模型请求分别37/45次。4B N03首次把工期字段提交到热工记录，应用拒绝后在四轮、15事件内完成纠正；不是首次正确。4B H04仍错误地归纳“两份记录因不同原因失效”，失效原因追溯与解释缺陷未关闭。两源码阶段合计48次API任务、142次模型请求，不能合成一个“最终准确率”。

随后全量回归发现工具定义为20,172字符，超过已有20,000字符预算。`3b63d6e`仅移除每个工具重复的根标题，缩至19,395字符；字段约束和可达定义保持原样，未放宽预算。相关62项通过，并另做真实模型及全量回归；最后两模型各3旧题、2新题形成所需产物，共29次真实请求。三个源码阶段合计58次API任务、171请求，不是同版本单一准确率。上述浏览器使用6315c6c，前端与最终版本一致，差异仅为该工具元数据精简；不能把不同源码的运行合称同一批。

浏览器实际运行3次模型任务/7次请求（双计划、双失效、单计划授权），另有1次在项目资料重绘后误用本地流程的任务。初次C01通过，初次C02未形成专业交付；显式重选模型后的C02和后续C03通过。当前热工页面与报告R=2.17一致，旧材料与碳报告均显示失效并不输出当前结果。截图确认批量子操作及暂缓状态；小字、长输入区和信息密度问题仍存在。浏览器脚本在读取缺失字段及使用隐式上下文新建页面时的两个错误均留证，修正脚本后继续；应用没有观察到pageerror。
