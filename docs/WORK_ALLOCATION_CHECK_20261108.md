# 工作安排复查：为什么提分慢（2026-11-08）

结论：存在局部兜圈，执行安排需要纠偏。95+目标不变，但不承诺靠补丁数量或反复测试能达到。此次不重评分、不发布代码。

## 已核实的问题

1. PR46–52七次发布，历史开发复评从76到77。来源失效、错误几何等修复必要，但分页/状态/备份兼容返工挤占主线；返工通过不能计作新业务能力。
2. 历史77中74可定位原子项，另外Agent2分、文件1分缺少明确归属。74不是重新验收分，77不是本轮保证分。下一综合复评必须重核，不能临时搬分。
3. 当前Agent输出批次v1/v2/v3，旧题自动通过分别2/4、2/4、3/4。v3开发侧留出题4/4，但这是小样本自动合同核验；原始结果仍标manual_review=pending，不能写成独立盲测100%。解释由应用按已核验来源生成，不代表模型自由文本推理全通过。
4. F01仍重复交付，耗尽5次模型响应；缺总R、层R及施工记录查询。它不是单靠多跑几次即可解决的失败。本批不得再次调同题并拿重跑结果替换首次失败。
5. 最新真实界面任务能交付R/U与查询说明；修改项目来源后旧数值和解释已撤下。但固定输入区域、长说明和原始字段增加阅读负担，不能据此宣称体验通过。
6. “Agent完全修好以后再做其他能力”的无限串行门槛可能形成新循环。安全拒绝/来源正确性是交付底线；某项自主任务失败需要保留并限制使用，但不应自动阻塞与它无依赖的确定性工程工作流开发。

## 立即执行的安排

|顺序|只交付什么|收口/转向规则|
|---|---|---|
|当前Agent批次|完成已有实现的原文核查、最终差异审查、必要CI和证据归档；标明失败和适用范围|不加第三种模型、不追加同题调参、不扩大工具协议；有严重错误先限制该路径。普通遗留转待办，不能把实验性Agent称为可靠完成|
|随后工程主流程|一套公开可复核输入：文件→材料/专业数量→两种方案→成本/碳→同源报告|预先固定人工量单、单位/来源/边界和容差；完整用户操作通过才关闭该业务缺口，不能以接口数量代替|
|其后原任务缺口|规范版本冲突、退化图纸和跨图关系、并发/恢复等|分别对应原八维子项；公开可验先做，真正依赖授权资料/专家/生产环境的单列|
|综合复评|重核原八维以及3分归属不清增量|允许降分；不改权重、不保证95；仅按剩余未过项继续|

全局视觉改版仍遵循用户顺序；阻碍阅读、遮挡结果等基本可用性可随主流程修。95+达成前不扩大训练。catalog支线继续保留不扩展。

## 防止再次兜圈的检查

- 每批只报告“用户新增能完成什么、未通过什么、下一项是什么”；测试数只作证据。
- 同一缺陷最多连续两个修正批次；仍未过则记录根因/边界并重新选择方案，不能无限叠提示词、例外规则或模型更换。严重问题不能被转待办后宣称解决。
- 专项验证随修改；相同源码已通过的全量不重复跑。完整能力批统一CI/发布，不一补丁一全套。
- 如果连续两批没有关闭原验收业务缺口，必须重新调度；不得自动增加评分条件来解释停滞。
- 评分只在能力里程碑或综合复评时更新，不把编写报告、回归修复、重复基准计为新增分值。
