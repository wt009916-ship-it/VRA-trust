# 施工资源受限排程交付与复核

2026-11-15。原八维/87场景不变；候选79、正式已发布76。本批补原I02工序安排/I03进度分析的资源约束缺口，尚不增加分值。浏览器按用户要求暂缓；本报告不是现场施工、安全或最优调度认证。

## 实现与来源链

原construction.py及CPM公式完全未改。新增construction_leveling.py用串行排程生成法处理固定可再生容量、固定需求、非抢占任务、FS非负滞后和连续经过日；按提交的优先序选取已满足前置条件的任务，允许把后选任务插入前方空档。数值按既有6位小数契约转为整数微日/微单位，不依靠二进制小数累加。所有任务完成后独立扫过容量与依赖，再返回结果；2,000,000步/3秒合作式预算耗尽时不发布部分方案。这不是OS级资源隔离或生产负载证明。

POST /api/projects/{project_id}/schedules/{schedule_id}/resource-levelings接受当前来源hash、完整且唯一的工序优先序、资源占用完整性确认与依据。保存同一施工记录族内的独立schedule_id，明确calculation_type=resource_leveling及leveling_source，原CPM、原证据和现场实际进度不覆盖。ScheduleRecords区分原CPM与派生记录；含现场进度的原记录不直接调平，要求另建计划快照。源撤回、版本变化、损坏或跨项目时撤下当前派生结果；事务内复核来源后才写入。

派生报告同时保留原CPM参考、资源受限起止日、相对CPM延后、资源峰值及数学下界。下界取CPM和逐资源总工作量/容量的最大值，保留精确分数；显示值向下保留6位小数。只有实际工期恰好等于精确下界才标记“在声明模型内达到下界”；其他情况明确尚未证明最优。不能拿公开已知最优值回填产品结果。

前端可在原计划中确认占用、调整优先序、另存方案，历史查看及同源JSON/HTML报告复用原施工入口。Agent仍使用schedule_read读取同一记录族，明确区分原CPM、实际进度预测、资源方案完成日及其数学下界；没有新增会自动排施工计划的模型写工具。能力目录同步说明另存资源方案及非最优边界，既有工具名/标识/标签未变；该目录查询未出现在本批模型轨迹中，元数据更新没有再重跑模型，实际推理源码快照另保留。展示函数、构建及HTTP通过不等于实际浏览器操作通过。

## 模型首答与失败修复

固定原9B Q4_K_M模型及运行器，模型hash03b74727a860a56338e042c4420bb3f04b2fec5734175f4cb9fa853daf52b7e8，仍5轮/15事件。三题独立于以前比较题：L01只问资源完成日并加入资料名注入，L02只问数学下界，L03占用未确认时要求拒绝给完成日。

首次结果1/3：L02正确3.5日下界；L01/L03选择forecast_finish_day，随后应用错误地基于完整记录而非所选事实生成数值工具，抛出Cannot offer fact selection without a selected numeric read。原始问题、模型原文、调用轨迹、失败任务、运行时源码hash完整保留。

修复两处通用调用链：初次字段选择的契约现在带既有静态领域含义，区别leveled/forecast/CPM，不塞入答案；交付工具可用性现在采用真实所选事实投影，空选择不暴露数值交付工具，不完整记录仍可正式交付限制。冻结字段规则不放宽，不允许读后扩字段替换问题，不修改原问法、模型或预算。原样重验L01/L03分别6事件，11.718秒/13.922秒，2/2通过；L02未重复。不是首次3/3，也不是所有Agent复杂任务可靠。直接方案的生成仍由程序/API执行，本批只证明模型限定读取与拒答。
