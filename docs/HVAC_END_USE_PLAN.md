# 下一能力批：实际暖通设备能耗分项（执行前计划）

执行前计划保留。2026-11-09已完成限定实现、真实原生与本地HTTP验收，详HVAC_END_USE_DELIVERY.md；精确提交三CI已通过，实际证据见交付及复评，不把本计划当作证明。原八维/87项、95+、后训练与整体前端的顺序不变。

当前代码定位：backend/core.py:parse_sql 读取 End Uses 的 Total End Uses 行形成 energy_by_carrier_kwh，未交付逐用途的供暖、制冷、风机及水泵能耗账；backend/ideal_loads.py 提供理想系统热量边界，不是实际设备电耗。不能从过期报告重复开发已有年度能耗/显潜热/时间步检查。

目标是原 B03/B05 的限定能力增量：对明确设备及能耗载体，输出有原生 SQL 位置的用途分项、与载体/场地总量的核对及适用范围。不得把理想负荷按猜测 COP 自动换成耗电，也不得把模拟量写成实测能耗。

顺序与退出要求：
1. 核对当前可用 EnergyPlus 版本和官方输入/输出文档；挑选有许可公开参考模型或自建受控模型，明确实际设备、控制、气象和年度/设计日范围。先验证该范围能真实运行，未知模型不默认支持。
2. 运行前冻结新的输入、独立核算方法、容差与拒绝案例。至少覆盖供暖/制冷与风机/水泵分项、多个能源载体、零用量、缺行/重复/错单位及混合理想/实际系统。逐项独立源数据核对与物理参考计算分列，不能把同一 SQL 再加一次当作物理独立验证。
3. 真实计算结果、API、报告及功能界面同源交付；缺分项或无法对账返回未知/缺口，来源变化撤回；原件与旧记录保留。若修改物理身份，记录旧运行保守 stale，不改旧 hash；先检查是否可用独立诊断衍生模块避免无关物理失效。
4. 在隔离数据库完成真实 HTTP 流程、来源撤回及项目归属，完成相关前端逻辑和精确提交 CI。浏览器仍按用户选择待验。每个明确失败只修原因、限定复测；旧 N/S/T/U 模型题、已通过 PR68 与 PR69 专项无新变更不重跑。

停止条件：未取得所需真实原生输出或独立参考不成立时，明确记录该范围不成立，不用模拟回执填补、不转成重复提示词筛查。专业分仅在能力与新参考证据覆盖原扣分项后复评，不能事先承诺本批增加几分。实楼校准、设备选型合规及专业签署依旧待外部材料/审查。
